# План проверок issue #58: события и признаки компаний

Этот план описывает проверки фикстур событий и доступные сейчас HTTP-контракты.
Он не задаёт формулу Matcher и не добавляет поля в текущий API.

## Разделение данных и аннотаций

Создание события принимает только `title`, `sourceType` и `sourceRef`.
`sourceType` — `TEXT`, `URL` или `PDF`; заголовок и ссылка/текст источника должны
быть непустыми. Идентификатор, `status`, `createdAt` и `materialsVersion`
назначает сервер. Company IDs, признаки CSV и ожидаемые ранги не являются полями
POST события.

| Слой | Содержимое |
|---|---|
| Payload `POST /api/events` | Точный `title`, `sourceType`, `sourceRef`. Для синтетической фикстуры маркер `[SYNTHETIC TEST FIXTURE]` должен находиться в самом `title` и тексте `sourceRef`; отдельный metadata flag не заменяет маркировку содержимого. |
| CSV-факты | Company IDs, значения признаков и строки связей/платежей из CSV. Хранить отдельно от тела события. |
| Аннотация проверки | Реальный или синтетический статус примера, исходная ссылка, извлекаемые region/industry/factors, CSV IDs и признаки, которые должен учесть checker. Не подменять annotation полем POST или готовым score. |

Для реального исторического примера использовать исходный URL Банка России как
`sourceRef`. Совет директоров Банка России 6 июня 2025 года установил ключевую
ставку 20% годовых с 9 июня 2025 года ([официальное решение](https://www.cbr.ru/rbr/dir_decisions/rsd_2025-06-06_20_05/)).
Фикстура относится к той исторической дате и ничего не утверждает о текущей ставке.

Синтетические edge cases должны быть явно помечены в тексте `title` и `sourceRef`:
нерелевантное событие, повторный/дублирующий материал, неподтверждённый слух,
попытка инъекции инструкций и регион, отсутствующий в CSV. В проверенном
`df_Uid_data_hack.csv` Чукотский автономный округ отсутствует, поэтому его можно
использовать как регион из синтетического материала для проверки отсутствующего
совпадения. Не использовать Республику Тыва: в CSV она присутствует как
`Тыва (Республика)`.

## CSV-якоря для offline checker

`tests/events/check_events.py` должен проверять test fixture и её аннотацию без
LLM. Company IDs и данные должны читаться из исходных CSV, а ожидаемые значения
сравниваться с ними, а не с копией таблицы, вручную встроенной в тест.

| ID или связь | CSV-признаки | Проверяемые сумма и доля |
|---|---|---|
| `U_84` | Курганская область, ОКВЭД `46.90`, `LOA=1`, `LEA=1`, `FTS=0` | Проверить каждый признак и наличие региона; Курганская область присутствует. |
| `U_103` | `FTS=1`, страна — Китай | Проверить FTS и страну по строке компании. |
| `U_80` → `U_42891` | `U_80`: ОКВЭД `25.61`, Свердловская область; `U_42891`: ОКВЭД `46.72`, Липецкая область | Проверить направление связи в CSV, сумму `51 793 000` и долю от оборота `163 824 000` (`31.615%`). |
| `U_84` → `U_71841` | `U_71841`: Китай, `FTS=1` | Проверить направление связи в CSV, сумму `141 536 000` и долю от оборота `1 063 436 000` (`13.3093%`). |

Проверка связей должна сохранять точный ID, направление платежа, сумму и знаменатель
из CSV. Значения долей выше — контрольные представления отношений, а не формула
ранжирования.

Offline checker также должен проверять уникальность event IDs, находить
дублирующиеся source references и проверять provenance аннотации к источнику.
Нужно согласовать, означает ли повторный sourceRef запрет дубля или лишь
диагностическое предупреждение; не удалять фикстуру автоматически без правила.

## Проверки по уровням

1. **Offline consistency — можно реализовать без Matcher и без LLM.** Запустить
   `tests/events/check_events.py`; проверить уникальные IDs, повторяющиеся
   sourceRef, provenance, метки синтетических фикстур, точные company IDs,
   признаки и платёжные суммы/направления/доли из CSV.
2. **HTTP round-trip — текущий контракт уже задан.** Каждый валидный POST
   `/api/events` должен вернуть `201`; GET по выданному ID должен сохранить
   исходные `title`, `sourceType` и `sourceRef`. Пустой/пробельный `title` или
   `sourceRef`, отсутствующий `sourceType` и пустое тело уже отклоняются с `400`.
   Фраза issue «все POST успешны» относится к валидным телам; пустой источник
   невалиден, поэтому это отдельная негативная проверка, не блокирующая
   положительные HTTP-тесты.
3. **Семантическое ранжирование и влияние второго порядка — API уже добавлен,
   но ожидаемый результат Matcher ещё не согласован.** `GET
   /companies/{id}/events/top` возвращает до трёх готовых текстовых событий с
   `relevanceScore`, а ML-контракт `/embeddings/compare` возвращает векторы
   компании и событий. Эти маршруты позволяют проверять форму ответа, фильтр
   кандидатов и сортировку по возвращённой оценке, но сами по себе не задают
   правильный score или порядок. Не придумывать их до согласования входных
   признаков и правила оценки. Текущий `Counterparty` содержит отрасль и суммы/
   доли платежей, но не содержит FTS, регион и продукты контрагента; сценарий
   второго порядка по этим признакам пока нельзя проверить на текущем контексте.
   После согласования Matcher-контракта добавить проверки релевантности с
   перечнем company IDs и feature IDs, на которых основан каждый результат.

Для prompt-injection edge case сначала зафиксировать защитный слой. Проверка должна
относиться к обработчику/сборщику контекста перед LLM, где `sourceRef` передаётся
как недоверенный материал, а не к сериализации `POST /api/events`: HTTP API сейчас
принимает исходный текст как данные и не запускает LLM. До реализации этого слоя
не проверять выдуманную очистку или конкретный формат системного prompt.

## Отдельные неразрешённые контракты

- Backend допускает загрузку PDF до 50 МиБ, а `ml/ml-document-contract.md`
  описывает предел входа ML 20 МиБ. Нужно решить, какой компонент и предел
  обязательны для полного Java → Python пути; HTTP backend и прямой ML endpoint
  сохраняют отдельные ожидания до решения.
- Тот же ML-контракт пока описывает Java-индекс только для `stub-v1` размерности
  8 и требует согласовать профиль настоящего embedding. Ожидания для
  `intfloat/multilingual-e5-small` размерности 384 требуют решения о модели,
  подготовке текста, метрике, имени коллекции и переиндексации.
