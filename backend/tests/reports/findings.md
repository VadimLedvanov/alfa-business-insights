## Находки baseline `99a182f`

- **ACL regression:** `InsightService.authorize` теперь пропускает любого пользователя с `ROLE_COMPANY_DIRECTOR` без проверки `user_company_access`. Требование компании-скоупированных прав не менялось: `doc/visionandscope.md` требует проверять право пользователя на компанию. Существующий `InsightApiIntegrationTest#rejectsAnonymousAndDirectorWithoutCompanyAccess` остаётся корректным регрессионным оракулом; не переклассифицировать его как устаревшее ожидание.
- **Имя Qdrant collection:** текущий `DocumentVectorStore` направляет non-stub модель в фиксированную `rag_documents`, тогда как `DocumentVectorStoreCollectionTest#multilingualE5UsesItsOwn384DimensionCollection` ожидает отдельное имя `knowledge_documents_intfloat_multilingual_e5_small_384`, а `ml/ml-document-contract.md` описывает согласование отдельной коллекции для настоящего профиля и переиндексацию. Это конфликт текущего refactor с документированным профилем и тестовым ожиданием; сам по себе он не доказывает смешивание результатов в рантайме: поиск фильтрует Qdrant payload по `embeddingModel` (`DocumentVectorStore.search`).
- **Пробелы покрытия новых API:** `GET /companies/{id}/events/top` проверяется HTTP-сценариями `CompanyUsersHttpE2eTest`: доступ по grant, запрет профиля и top без grant, а также исключение нового PROCESSING-события. Семантическое качество и порядок ранжирования top остаются непроверенными без согласованного oracle. `GET /companies/{id}/events/{eventId}/messages` и ML `POST /embeddings/compare` по-прежнему не имеют прямых тестов.
- **Дополнительный HTTP-контур на `126afd3`:** `CompanyUsersHttpE2eTest` создаёт трёх временных Keycloak-директоров с отдельными кредитным, торговым и невыданным профилями. Все шесть независимых запросов без grant (профиль и top для CREDIT→trade, TRADE→credit и UNASSIGNED→unassigned) получили HTTP 200 вместо ожидаемого 403; проверка оставлена как `known-defect`. `EventCatalogHttpE2eTest` проверяет HTTP-создание, чтение и список ровно 20 синтетических PR65-событий, включая фильтры и пагинацию. Финальный прогон подтверждает фильтры и пагинацию; семантическое ранжирование не проверяется, внешняя модель не вызывается.
- **Обновление ожиданий и очистки фикстур завершено:** валидная фикстура дополнена обязательными `significance` / `significanceReason`; teardown удаляет `dialog_messages` по точному набору test event/insight IDs до родительских строк из-за FK; фикстуры учитывают 50 тестовых READY-событий в чистой БД.
- **Риск upgrade миграции (не воспроизведён на существующей БД):** 50 seed-событий добавлены в уже существующий changeset `20261023-01`, checksum которого принят через `validCheckSum`. Тестовые БД создаются чистыми и не проверяют обновление ранее инициализированной БД; `validCheckSum` снимает проверку checksum, но не запускает уже выполненный changeset повторно. Для применённых баз нужен отдельный новый changeset с INSERT-ами.

## QA-001 — директор читает компанию без разрешения

- **Статус:** воспроизведено через HTTP, настоящий JWT Keycloak и PostgreSQL.
- **Приоритет:** P1 — пользователь с ролью директора может читать контекст компании,
  к которой ему не предоставлен доступ.
- **Версия:** исторически воспроизведено на `c7e67fa` (`dev`) и повторно подтверждено полным прогоном QA-5 на baseline `51faccf`. Production-код для этой находки не менялся.
- **Основание:** `doc/visionandscope.md`, раздел 2.4, поток «Вход»:
  Java проверяет подпись JWT **и право пользователя на компанию**;
  таблица `user_company_access` документирована как право работать с данными компании.

### Воспроизведение

1. В изолированной БД создать синтетическую компанию `e2e_<uuid>`.
2. Не создавать разрешение `user_company_access` для этой компании.
3. Получить настоящий токен пользователя `director` в Keycloak.
4. Выполнить `GET /api/companies/e2e_<uuid>` с этим токеном.

**Ожидается:** HTTP 403; контекст недоступной компании не раскрывается.

**Фактически:** HTTP 200 с профилем компании, пустыми платёжными связями
и перечнем отсутствующих данных.

**Регрессия:**
`backend/tests/e2e/company-context/CompanyContextHttpE2eTest.java`,
`TestE2ECompanyAccessRequiresGrant`.

### Причина по коду

`SecurityConfig` проверяет роль, а `CompanyController` передаёт идентификатор
в `CompanyContextService` без проверки пользователя и `user_company_access`.
Сама таблица доступа существует, но не участвует в этом пути чтения.

Добавить проверку права на компанию для директора. Системного администратора
обработать согласно согласованной политике. Проверить доступ до выдачи контекста;
сохранить функциональность доступа к разрешённой компании. Повторить эту
регрессию и полный набор.

Тест не отключён и не исключён из полного запуска. Общий прогон остаётся FAIL,
даже когда остальные тесты проходят и порог покрытия достигнут.

## Ограничения, которые не считаются подтверждёнными багами

## QA-002 — Feign принимает строковую координату embedding

- **Статус:** воспроизведено контрактным тестом production Feign с локальным HTTP-ответчиком; путь загрузки PDF этим тестом не проверяется.
- **Приоритет:** P2 — ответ ML с неверным JSON-типом проходит границу декодирования вместо отказа на контракте.
- **Основание:** [ML document contract](../../../ml/ml-document-contract.md), строки 165–168 требуют числовые значения координат.

### Воспроизведение

1. На случайном loopback-порту ответить синтетическим `stub-v1` JSON, где одна координата `embedding` задана строкой `"1.0"`.
2. Передать синтетический PDF через production Feign `DocumentAnalyzer`.

**Ожидается:** нарушение типа отклоняется на границе декодирования JSON согласно ML-контракту.

**Фактически:** Feign преобразовал строку в `Float(1.0)` и вернул валидный `DocumentAnalysis`; вызов `analyzer.analyze()` завершился без исключения; отдельная `validate()` этим тестом не вызывалась. Ошибка API загрузки HTTP 502 данным probe не воспроизводилась.

**Регрессия:** `backend/tests/integration/documents/DocumentAnalyzerJsonContractTest.java`, `TestIntegrationRejectStringEmbedding`.

Исправление production-кода не входит в текущую работу; регрессия сохраняется красной до исправления.


## QA-003 — отказ PDF без извлекаемого текста возвращается как 422

В `c7e67fa` Java-контракт исправлен: настоящий Python отвечает 422 для PDF без текста,
backend сохраняет этот статус и возвращает `retryable=false`; проверка подтверждает
компенсационную очистку метаданных и файлов. Историческое обобщение «ML outage = 502»
оказалось неверным тестовым ожиданием для явно сообщённой недоступности: текущий API
возвращает 503 `ML_UNAVAILABLE` с `retryable=true`. Некорректный ответ анализа остаётся
отдельным 502 `BAD_GATEWAY`; транспортные ошибки без явной причины следует классифицировать
отдельно, не переносить на них ожидания malformed-ответа.

Регрессии отказа без текста: `TestIntegrationRejectTextlessPdfWithoutArtifacts`,
`mlRejectsPdfOrIsUnavailableReturnsStatusAndCleansArtifacts`. Недоступность ML и
некорректный результат проверяются отдельно: `mlUnavailableReturns503AndCleansArtifacts`
и `invalidMlResponseCancelsUpload`; unit-проба доступности — `TestUnitCleanupAfterAnalyzerFailure`.

## Синхронизация с PR #49 и граничные размеры

На `242d7cf` лимит Java/Spring/БД — 50 МиБ, multipart-запроса и nginx — 51 МиБ.
Реальные HTTP-тесты проверяют 36 МиБ, 50 МиБ − 1 байт, ровно 50 МиБ,
50 МиБ + 1 байт и 51 МиБ. Первые три файла принимаются без изменения размера/хеша;
последние два дают 413 без изменения PostgreSQL и снимка файлового хранилища.
После отказа API отвечает на следующий запрос. Это снимает прежнюю статическую
находку про nginx 1m; старый PDF-отчёт относится к срезу до PR #49.

В `ml/ml-document-contract.md` пока остался лимит 20 МиБ. Его нужно согласовать
с новым контрактом Java 50 МиБ; текущий pytest проверяет общий актуальный порог 50 МиБ из Java OpenAPI
и обнаруживает, что Python не ограничивает размер. Это расхождение требований
отделено от подтверждённых сценариев загрузки через backend.

## QA-004 — факт без ссылки удаляется вместо понижения до вывода

- **Статус:** воспроизведено unit-тестом на историческом срезе `26ac72a` и подтверждено полным прогоном QA-5 на baseline `51faccf`.
- **Приоритет:** P2 — неподтверждённое утверждение теряется вместо сохранения как вывода с явно низкой уверенностью.
