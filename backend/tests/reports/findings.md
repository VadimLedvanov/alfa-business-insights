# Находки

## QA-001 — директор читает компанию без разрешения

- **Статус:** воспроизведено через HTTP, настоящий JWT Keycloak и PostgreSQL.
- **Приоритет:** P1 — пользователь с ролью директора может читать контекст компании,
  к которой ему не предоставлен доступ.
- **Версия:** повторно воспроизведено на `242d7cf` (`dev`). Production-код не менялся сверх входящих обновлений разработчиков.
- **Основание:** `doc/visionandscope.md`, раздел 2.4, поток «Вход»:
  Java проверяет подпись JWT **и право пользователя на компанию**;
  таблица `user_company_access` документирована как право работать с данными компании.

### Воспроизведение

1. В изолированной БД создать синтетическую компанию `e2e_<uuid>`.
2. Не создавать разрешение `user_company_access` для этой компании.
3. Получить настоящий токен пользователя `director` в Keycloak.
4. Выполнить `GET /api/companies/e2e_<uuid>` с этим токеном.

**Ожидается:** HTTP 403; контекст недоступной компании не раскрывается.

**Фактически:** HTTP 200 с профилем компании, пустыми платёжными связями
и перечнем отсутствующих данных.

**Регрессия:**
`backend/tests/e2e/company-context/CompanyContextHttpE2eTest.java`,
`TestE2ECompanyAccessRequiresGrant`.

### Причина по коду

`SecurityConfig` проверяет роль, а `CompanyController` передаёт идентификатор
в `CompanyContextService` без проверки пользователя и `user_company_access`.
Сама таблица доступа существует, но не участвует в этом пути чтения.

### Передать backend-разработчику

Добавить проверку права на компанию для директора. Системного администратора
обработать согласно согласованной политике. Проверить доступ до выдачи контекста;
сохранить функциональность доступа к разрешённой компании. Повторить эту
регрессию и полный набор.

Тест не отключён и не исключён из полного запуска. Общий прогон остаётся FAIL,
даже когда остальные тесты проходят и порог покрытия достигнут.

## Ограничения, которые не считаются подтверждёнными багами

- Настоящий Python-парсер проверен по HTTP и через backend/Qdrant. Embeddings остаются
  локальными `stub-v1`, размерность 8. Семантическая релевантность и внешняя LLM не проверялись.
- ML-инструкция рекомендует последовательные ordinal, а таблица контракта требует
  только уникальные неотрицательные номера. Приём ответа с пропуском номера
  не оформлен как дефект Java: требование на отклонение такого ответа неоднозначно.
- Зелёный smoke подтверждает критические рабочие пути, но не снимает QA-001.

## QA-002 — Feign принимает строковую координату embedding

- **Статус:** воспроизведено контрактным тестом production Feign с локальным HTTP-ответчиком; путь загрузки PDF этим тестом не проверяется.
- **Приоритет:** P2 — ответ ML с неверным JSON-типом проходит границу декодирования вместо отказа на контракте.
- **Основание:** [ML document contract](../../../ml/ml-document-contract.md), строки 165–168 требуют числовые значения координат.

### Воспроизведение

1. На случайном loopback-порту ответить синтетическим `stub-v1` JSON, где одна координата `embedding` задана строкой `"1.0"`.
2. Передать синтетический PDF через production Feign `DocumentAnalyzer`.

**Ожидается:** нарушение типа отклоняется на границе декодирования JSON согласно ML-контракту.

**Фактически:** Feign преобразовал строку в `Float(1.0)` и вернул валидный `DocumentAnalysis`; вызов `analyzer.analyze()` завершился без исключения; отдельная `validate()` этим тестом не вызывалась. Ошибка API загрузки HTTP 502 данным probe не воспроизводилась.

**Регрессия:** `backend/tests/integration/documents/DocumentAnalyzerJsonContractTest.java`, `TestIntegrationRejectStringEmbedding`.

Исправление production-кода не входит в текущую работу; регрессия сохраняется красной до исправления.


## QA-003 — ошибки разбора PDF возвращаются как недоступность ML

На `242d7cf` настоящий Python отклоняет PDF без текста кодом 422,
а Java отвечает `503 ML_UNAVAILABLE`, `retryable=true`.
Текущий ML-контракт требует Java 502 для ошибок Feign и некорректного ответа;
`DocumentService.analyze` перехватывает все RuntimeException без классификации.
Повтор неизменённого PDF не исправляет отсутствие текста.

Согласовать коды для входной ошибки, некорректного результата и transport outage;
обновить код и контракт совместно. Компенсационная очистка проходит.
Регрессии: `TestIntegrationRejectTextlessPdfWithoutArtifacts`,
`invalidMlResponseCancelsUpload` (некорректные DTO/исключение Mockito-анализатора), `TestUnitCleanupAfterAnalyzerFailure`.
Последняя проверка также отражает изменение старой политики ошибок: 503 при настоящем
outage может быть верным решением, но документация пока требует 502.

## Материалы демо и следующие блокеры

Все девять оригинальных PDF из предоставленного архива получили от настоящего
локального Python API `422 «В PDF нет текста»`. У всех 64 страниц отсутствует
извлекаемый текстовый слой; нужен OCR либо явное решение по материалам приёмки.
`FI_Strategy_3Q26_22072026.pdf` — 34 890 230 байт. PR #49 поднял лимит backend до 50 МиБ, поэтому прежний блокер размера 20 МиБ снят; OCR по-прежнему отсутствует.
Полностью image-only PDF корректно отклоняется узким текущим контрактом,
но реальный демо-набор этим не поддерживается.

Статические блокеры: Python не реализует используемый Java `POST /embeddings`,
профиль настоящих embeddings не согласован,
публичный Qdrant обходит Java ACL, frontend пока заглушка.
Эти замечания требуют отдельных воспроизведений/согласования; полный сгруппированный
отчёт подготовлен отдельно, инструкция запуска ими не перегружается.


## Синхронизация с PR #49 и граничные размеры

На `242d7cf` лимит Java/Spring/БД — 50 МиБ, multipart-запроса и nginx — 51 МиБ.
Реальные HTTP-тесты проверяют 36 МиБ, 50 МиБ − 1 байт, ровно 50 МиБ,
50 МиБ + 1 байт и 51 МиБ. Первые три файла принимаются без изменения размера/хеша;
последние два дают 413 без изменения PostgreSQL и снимка файлового хранилища.
После отказа API отвечает на следующий запрос. Это снимает прежнюю статическую
находку про nginx 1m; старый PDF-отчёт относится к срезу до PR #49.

В `ml/ml-document-contract.md` пока остался лимит 20 МиБ. Его нужно согласовать
с новым контрактом Java 50 МиБ; текущий pytest проверяет общий актуальный порог 50 МиБ из Java OpenAPI
и обнаруживает, что Python не ограничивает размер. Это расхождение требований
отделено от подтверждённых сценариев загрузки через backend.
