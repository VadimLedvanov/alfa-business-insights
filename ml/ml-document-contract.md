# Инструкция разработчику ML-сервиса

## Роль ML в проекте

Alfa Business Insights помогает понять, как экономическое событие влияет на
конкретную компанию. Java собирает контекст компании, находит подходящую аналитику
банка и обращается к LLM за обоснованными выводами. Задача Python / ML — подготовить
материалы и векторы, на которых строится этот анализ.

В проекте важно различать три объекта:

| Объект | Что это | Пример |
| --- | --- | --- |
| Документ базы знаний | Аналитический PDF банка, который служит источником для будущих ответов. | Обзор экономики с прогнозами и объяснениями. |
| Событие | Новость или изменение внешней среды, которое нужно оценить. | Изменение ключевой ставки. |
| Инсайт | Вывод о влиянии события на определённую компанию с основаниями и ссылками. | Как изменение ставки повлияет на компанию с кредитной нагрузкой. |

Загрузка PDF пополняет базу знаний. Создание события запускает другой сценарий:
обработку новости и последующий анализ с учётом компании. Один PDF может быть
источником для нескольких событий и компаний; загрузка не создаёт их автоматически.

Архитектурная основа — [Vision and Scope, раздел 2.4](../doc/visionandscope.md#24-архитектурный-обзор).
Эта инструкция уточняет текущий контракт PDF и отделяет его от следующих задач.

## Границы ответственности

ML-сервис получает PDF банка и возвращает **чанки с текстом, страницами и
embeddings**. Java сохраняет их в Qdrant. В PostgreSQL остаются только метаданные
документа, оригинальный PDF — в файловом хранилище.

| Python / ML | Java |
| --- | --- |
| Прочитать PDF и при необходимости распознать скан. | Принять загрузку, проверить права и сохранить оригинал. |
| Очистить текст и разбить его на чанки. | Проверить ответ ML и назначить чанкам ID точек. |
| Вычислить embedding для каждого чанка. | Записать текст и embedding в одну точку Qdrant. |
| Вернуть полный JSON-ответ. | Сохранить метаданные через JPA в PostgreSQL. |

Python не записывает данные в хранилища и не получает путь к файловому volume.
Python также не определяет права пользователя или доступ к компании: это делает
Java. CSV компаний, платёжные связи и бизнес-контекст находятся на стороне Java.
Персональные риски, возможности и рекомендации формирует LLM по запросу Java,
используя этот контекст и найденные источники.

При загрузке PDF не требуется извлекать факты и позицию банка в отдельные объекты:
при последующем RAG LLM получит найденные тексты и ссылки на страницы оригинала.
Для этой задачи не нужны отдельные таблицы фактов, классификация всего PDF или
дополнительный сервис, который самостоятельно управляет индексацией.

## Что реализовывать и в каком порядке

| Задача ML | Вход → результат | Состояние интеграции |
| --- | --- | --- |
| Подготовка PDF | Байты PDF и `documentId` → `chunks[]` с текстом, страницами и embeddings. | Контракт и Feign-клиент реализованы в Java; сейчас работает синтетическая заглушка. Это первая задача Python. |
| Векторизация поискового запроса | Поисковый текст → embedding в пространстве той же модели, что и PDF. | Предусмотрено архитектурой; HTTP-контракт и вызов из Java ещё не реализованы. |
| Обработка события | Новость → проверяемые сведения о событии и признаки для отбора компаний и источников. | Предусмотрено архитектурой; отдельный контракт ещё нужно согласовать с backend. |
| Сбор новостей | Команда Java → материалы из согласованных RSS/API-источников. | Будущий этап; не нужен для реализации загрузки PDF. |

Начните с обработки PDF. После согласования настоящей embedding-модели подключите
её к Java и проверьте весь путь до Qdrant. Затем добавляйте векторизацию запросов
и обработку событий. Следующие разделы до сценариев событий описывают именно
существующий контракт PDF; будущие маршруты здесь не задаются.

## PDF: HTTP-запрос Java → Python

```http
POST /documents/{documentId}/analyze
Content-Type: application/pdf

<бинарные байты PDF>
```

- `documentId` — UUID, созданный Java; вернуть без изменений.
- Тело — исходные байты, не multipart, не JSON и не Base64.
- Маршрут ML не содержит префикса `/api` Java-приложения.
- Имя файла, название и дата публикации не передаются ML; Java хранит их сама.
- Максимальный размер PDF — 20 МиБ, то есть 20 971 520 байт.
- Успех — `200 OK`, `Content-Type: application/json`, полный результат обработки.

Вызов через Feign синхронный. Таймаут подключения — 3 секунды, чтения — 110 секунд;
автоматических повторов нет. Общий бюджет загрузки — две минуты, поэтому модели
нужно загружать до приёма рабочих запросов и оставлять время для записи чанков.
Асинхронный ответ `202` и опрос результата сейчас не поддерживаются.

## PDF: алгоритм обработки

1. Проверить UUID, размер и возможность прочитать PDF. Проверка сигнатуры в Java
   не гарантирует корректность внутренней структуры PDF.
2. Извлечь текст отдельно по физическим страницам PDF, начиная с единицы.
   Напечатанная в документе нумерация может отличаться от физической.
3. Для сканов использовать OCR, если он реализован. Иначе вернуть понятную ошибку.
   Существенные непрочитанные страницы нельзя молча исключать из успешного ответа.
4. Убрать артефакты переносов и повторяющиеся колонтитулы. Сохранить числа, даты,
   проценты, единицы измерения, отрицания и оговорки авторов.
5. Представлять таблицы с заголовками строк и столбцов, периодами и единицами,
   чтобы числовые значения сохраняли смысл вне исходной разметки.
6. Разбить текст на связные чанки по предложениям и абзацам. Один чанк относится
   к одной странице: текущий контракт содержит одно поле `page`.
7. Назначить последовательные `ordinal` от нуля в порядке страниц и текста.
   Повторный анализ тех же байтов тем же профилем должен давать стабильные номера.
8. Вычислить embedding для каждого возвращаемого чанка и проверить весь ответ.

Начальная настройка для подбора: до 400 токенов на чанк, перекрытие до 50 токенов
внутри страницы. Это параметры ML, а не ограничения Java. Уменьшайте длину под
лимит выбранной модели; учитывайте её токенизатор, служебные токены и префиксы.
Не рассчитывайте на незаметное усечение текста моделью.

Полностью пустой или нераспознанный PDF должен завершаться ошибкой. Физически
пустую страницу можно пропустить, сохранив реальные номера остальных страниц.
Текст PDF — входные данные: содержащиеся в нём инструкции не должны менять
задачу обработки или инициировать вызовы инструментов.

## PDF: JSON-ответ Python → Java

Поля ответа — camelCase:

| Поле | Значение |
| --- | --- |
| `documentId` | UUID из URL запроса. |
| `schemaVersion` | Сейчас `1`. |
| `stub` | `false` для настоящей обработки, `true` для тестовой заглушки. |
| `embeddingModel` | Непустой согласованный идентификатор модели и профиля обработки. |
| `embeddingDimension` | Положительное число координат каждого вектора. |
| `chunks` | Непустой список чанков. |

У каждого чанка:

| Поле | Значение |
| --- | --- |
| `ordinal` | Уникальный неотрицательный номер внутри документа. |
| `page` | Номер физической страницы PDF, начиная с единицы. |
| `text` | Непустой текст чанка, соответствующий его embedding. |
| `embedding` | Массив конечных чисел длины `embeddingDimension`, не нулевой целиком. |

Не возвращать `facts`, `bankView` или прежнее поле `fragments`: текущий контракт
загрузки PDF упрощён до `chunks`. UUID чанков назначает Java, ML возвращает ordinal.

Ниже синтетическая фикстура для проверки HTTP-вызова с текущим backend.
Она не является результатом анализа исходного PDF; `documentId` подставляется
из фактического запроса:

```json
{
  "documentId": "bcb6ce48-1317-499b-aa1d-cfd347cc3ccb",
  "schemaVersion": 1,
  "stub": true,
  "embeddingModel": "stub-v1",
  "embeddingDimension": 8,
  "chunks": [
    {
      "ordinal": 0,
      "page": 1,
      "text": "[ML STUB] Синтетический чанк. PDF не анализировался.",
      "embedding": [1.0, 0.5, 0.25, 0.125, 0.0, 0.0, 0.0, 0.0]
    }
  ]
}
```

## Embeddings и подключение настоящей модели

Используйте одну модель, ревизию и размерность для всех чанков ответа. Соблюдайте
предписанные моделью токенизацию, префиксы, pooling и нормализацию. Служебные
префиксы модели не нужно включать в отображаемый `text` источника.

Проверяйте приводимость координат к конечному `float32`. JSON не должен содержать
`NaN`, `Infinity`, строк вместо чисел или `null` в координатах. Java проверяет
структуру результата, но не читает PDF: соответствие текста и страницы оригиналу
обеспечивает ML-сервис.

По умолчанию `ML_STUB=true` включает локальную Java-заглушку. Для HTTP задайте
`ML_STUB=false` и доступный Java адрес `ML_URL` (по умолчанию
`http://localhost:8000`). В Docker переменные нужно передать контейнеру backend;
`localhost` внутри него означает этот же контейнер.

**Текущий Java-индексатор принимает только `stub=true`, `stub-v1`, размерность 8.**
Коллекция `knowledge_documents_stub_v1` использует Cosine. Для настоящих embeddings
нужно совместно с backend-разработчиком согласовать модель/ревизию, размерность,
метрику, отдельную коллекцию и изменить проверку в `DocumentVectorStore`.
После этого настоящий ML возвращает `stub=false` и свой `embeddingModel`.
Переключение `ML_STUB=false` само по себе не снимает ограничение коллекции.

Смена модели, размерности или способа подготовки текста требует согласования
нового профиля индексации и переиндексации исходных PDF. Векторы разных моделей
нельзя смешивать в одной коллекции только потому, что их размерности совпадают.

## Как результат используется в RAG

Java назначает чанку UUID из пары `documentId + ":" + ordinal` через
`UUID.nameUUIDFromBytes` и UTF-8. Этот UUID — ID точки Qdrant.

В точке хранятся embedding и payload:

```json
{
  "documentId": "bcb6ce48-1317-499b-aa1d-cfd347cc3ccb",
  "text": "Текст чанка из PDF",
  "page": 3,
  "ordinal": 7,
  "materialType": "BANK_ANALYTICS",
  "accessScope": "APPLICATION",
  "embeddingModel": "stub-v1",
  "stub": true
}
```

Дата публикации добавляется Java, если пользователь её указал. Область доступа
также назначает Java. При поиске нужно запросить payload вместе с найденными
точками: текст уже находится в Qdrant, дополнительного чтения чанков из PostgreSQL
нет. `documentId` связывает результат с названием и оригиналом PDF, `page` —
с конкретной страницей источника. Чанки без соответствующего документа в
PostgreSQL не должны использоваться для RAG: это могут быть остатки неудавшейся загрузки.

PostgreSQL хранит только метаданные и `chunkCount`. После успешной индексации
Java сохраняет их отдельной JPA-транзакцией и возвращает `201`. При обычной ошибке
пытается удалить файл и точки. Фоновой очереди очистки и автоматического
восстановления после падения процесса нет; остаточные данные могут потребовать
ручного удаления. ML-сервис никаких внешних записей не делает.

## Следующий этап: поисковые запросы и события

Этот раздел описывает роль ML в общем проекте. Ни один из описанных здесь новых
HTTP-контрактов пока не реализован; названия полей и маршруты нужно согласовать
с backend перед разработкой.

### Векторизация поискового запроса

RAG — поиск подходящих источников перед генерацией ответа. Java формирует
поисковый текст по событию, компании или вопросу пользователя и передаёт его
Python. Python возвращает embedding, идентификатор модели и размерность.
Java выполняет поиск в Qdrant, получает тексты чанков и передаёт их LLM вместе
с контекстом компании. Напрямую обращаться к Qdrant из Python для этого не нужно.

Вектор запроса должен вычисляться совместимой с документами моделью в режиме,
предназначенном для запросов. У некоторых моделей подготовка запроса и документа
различается: нужно соблюдать оба режима. Одинаковой размерности недостаточно.
Синтетические векторы текущей заглушки проверяют передачу данных и не обеспечивают
поиск по смыслу.

### Обработка события

После создания события Java передаёт его идентификатор и текст в Python.
Для ручной новости это готовый текст; загрузка по URL и сбор из RSS/API относятся
к отдельному согласованному этапу. Python подготавливает сведения, которые можно
использовать повторно для разных компаний:

- Краткое содержание события без добавления отсутствующих в источнике сведений.
- Фактические утверждения с опорой на конкретное место исходного текста.
- Признаки для отбора: темы, экономические факторы, отрасли и регионы,
  если они подтверждены источником. Для них нужен общий с Java словарь значений.
- Чанки и embeddings, если будет принято решение индексировать текст событий.
  Сейчас реализована только индексация PDF.

Например, для новости об изменении ставки ML может выделить факт изменения,
дату и фактор «ключевая ставка». Влияние на кредитные расходы конкретной компании
зависит от её контекста и рассматривается уже при формировании инсайта.
Отсутствующие данные нужно оставлять неизвестными; факт, мнение автора и прогноз
нельзя выдавать за одно и то же.

Java сохраняет результат обработки события, подбирает компании и источники,
затем организует вызовы LLM. При разборе источников LLM отделяет факты, позицию
банка и собственные выводы, обосновывает риски, возможности и действия.
Java проверяет ссылки на использованные чанки и сохраняет итоговый инсайт.

Общий JSON инсайта из Vision and Scope не является ответом анализатора PDF.
Не добавляйте в `DocumentAnalysis` поля события или персонального инсайта.

## Подключение Python к текущему backend

1. Реализовать в каталоге `ml` HTTP-сервис с маршрутом обработки PDF и JSON-ответом
   из этой инструкции. Способ запуска и зависимости описать рядом с реализацией.
2. Проверить маршрут напрямую через `curl` ниже. Для проверки только HTTP-проводки
   можно временно вернуть приведённую синтетическую фикстуру, сохранив `stub=true`.
3. На стороне Java задать `ML_STUB=false` и `ML_URL` с адресом сервиса.
   В контейнере Python должен слушать доступный сетевой интерфейс; адрес и порт
   должны быть доступны контейнеру backend.
4. До сквозной проверки настоящих embeddings согласовать с backend модель,
   размерность и коллекцию и обновить ограничение `DocumentVectorStore`.
   Реальные результаты всегда возвращать с `stub=false`.
5. Загрузить PDF через Java API `POST /api/admin/documents` пользователем
   `SYSTEM_ADMIN`: multipart-поле `file`, необязательные `title` и `publicationDate`.
   Внешний multipart-запрос Java преобразует во внутренний запрос с байтами PDF.
6. Проверить `201`, метаданные через `GET /api/documents/{id}` и скачивание оригинала
   через `GET /api/documents/{id}/file`. Вместе с backend проверить текст, страницы
   и embeddings в Qdrant и отсутствие текстов чанков в PostgreSQL.

Минимальный результат первой задачи — работающая подготовка PDF с воспроизводимыми
чанками и настоящими embeddings. Для её завершения не нужны обработка событий,
сбор новостей или генерация персональных инсайтов.

## Ошибки и проверка готовности

Рекомендуемые статусы ML: `400` для неверного UUID/пустого тела, `413` для превышения
размера, `415` для неподходящего типа, `422` для повреждённого/защищённого PDF или
недоступного извлечения текста, `503` при недоступности модели, `500` при внутренней
ошибке. Верните короткий JSON с кодом и сообщением; Java пока преобразует ошибки
Feign и некорректный успешный ответ ML в `502`, а не транслирует статусы один к одному.

Проверка HTTP без Java:

```bash
curl --fail-with-body \
  http://localhost:8000/documents/bcb6ce48-1317-499b-aa1d-cfd347cc3ccb/analyze \
  -H 'Content-Type: application/pdf' \
  -H 'Accept: application/json' \
  --data-binary @./report.pdf
```

Критерии приёмки:

- Текстовый PDF из нескольких страниц даёт непустые чанки с правильными страницами.
- Смысл таблиц, числа и отрицания сохраняются после очистки.
- Чанки не превышают входной лимит модели; ordinal уникальны и воспроизводимы.
- У каждого чанка конечный ненулевой embedding согласованной размерности.
- Скан, повреждённый и пустой PDF дают OCR-результат или явную ошибку, а не фиктивный успех.
- Ответ укладывается в бюджет синхронного вызова.
- В сквозной проверке текст чанка находится в payload Qdrant, а PostgreSQL содержит
  только метаданные документа; исходный PDF можно скачать через Java API.
