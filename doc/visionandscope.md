## 1. Бизнес-требования

### 1.1 Контекст

Крупный бизнес (выручка свыше 15 млрд ₽) работает с большим числом контрагентов, сложными цепочками поставок и сильно
зависит от внешних факторов: ставки, курса, цен на сырьё, регулирования. У таких компаний уже есть собственная
аналитика, поэтому руководителю нужна не новость, а понимание её влияния на *его* компанию.

У Альфа-Банка есть экспертиза Центра макроэкономических исследований (девять аналитических материалов в кейсе), опыт
цифровых инструментов для бизнеса («Альфа Босс») и обезличенные данные о клиентах: профили компаний, группы, связи через
физлиц и платёжный граф. Эти активы сегодня не соединены в один продукт для крупного бизнеса.

### 1.2 Бизнес-возможность

Большинство решений в этой нише строят ленту «новости по отрасли клиента». Это легко повторить, и это не отвечает на
вопрос руководителя «что это значит для нас». Возможность - продукт, который:

- определяет значимость события по признакам конкретной компании и её окружения, а не только по отрасли;
- учитывает влияние второго порядка через контрагентов и группу компаний (платёжный граф, `GROUP_ID`, связи через
  физлиц);
- объясняет вывод словами банка, с прозрачным разделением фактов, позиции Альфа-Банка и выводов модели;
- предлагает следующее действие, в том числе релевантный банковский продукт.

Для банка это усиление роли партнёра крупного клиента и канал нативного предложения продуктов; для хакатона —
дифференциатор, который сложно воспроизвести за те же пять дней.

### 1.3 Бизнес-цели и критерии успеха

| ID   | Цель                                                | Измеримый критерий                                                                                                                                                    |

## 2. Видение решения

### 2.1 Формулировка видения

Для руководителей крупного бизнеса — клиентов Альфа-Банка, которые ежедневно принимают решения в условиях изменений
рынка и не хотят читать ленту новостей, **«Alfa Business Insights»** — это сервис внутри Альфа-Банка, который отбирает
значимые для конкретной компании события, объясняет их влияние через признаки компании, её группы и контрагентов и
показывает, какие выводы основаны на экспертизе банка, а какие сформированы AI. В отличие от новостных агрегаторов и
сервисов пересказа новостей, наш продукт строит карту влияния по платёжному графу и финансовой структуре клиента,
сохраняет связь каждого вывода с источником и предлагает следующее действие.

### 2.3 Принципы продукта

1. **Разделяем слои.** Подтверждённые факты, позиция банка, выводы AI и гипотезы никогда не смешиваются в одном абзаце.
2. **Не приписываем банку.** Если подходящей аналитики нет, об этом сказано прямо; у прогноза видны дата и период.
3. **Каждый вывод — со ссылкой.** Утверждение без фрагмента-основания либо помечается как вывод AI, либо не
   показывается.
4. **Честность о пробелах.** Отсутствие данных о компании или контрагенте — часть ответа, а не причина для домысла.
5. **Внешний текст — данные, не команды.** Новости и PDF не могут управлять агентом.
6. **Общий алгоритм для любой компании.** Никаких заранее написанных ответов под демо.

### 2.4 Архитектурный обзор

Решение следует согласованной компонентной диаграмме (Архитектура, 21.10.2026): Java Backend — единственный центр управления анализом и записи в хранилища; Python подготавливает материалы и в хранилища не пишет; Keycloak отвечает за идентификацию; модели вызываются двумя компонентами с разными целями. Агентная логика реализуется командой самостоятельно, без готовых мультиагентных систем.

**Компоненты**

| Компонент | Тип | Ответственность | Взаимодействия |
|---|---|---|---|
| Frontend | Компонент | Вход, выбор компании, оболочка интернет-банка с виджетом «Радар», лента инсайтов, подробный разбор, карта влияния, источники, уточняющие вопросы, обратная связь | → Keycloak (OIDC / PKCE) для входа; → Java Backend (API + JWT). Обращается только к Java |
| Keycloak | Компонент | Пользователи, вход и выход, сессии, выдача токенов доступа | ← Frontend (OIDC / PKCE); ← Java Backend (JWKS — ключи для проверки JWT) |
| Java Backend | Компонент (Spring Boot) | Центральный компонент. Проверка JWT и доступа пользователя к компании; контекст бизнеса и группы (Profiler); ранжирование (Matcher); AI-оркестрация (Interpreter): план, выполнение инструментов, поиск, проверка ссылок на фрагменты, критик, доработка; ответы на вопросы; кэш; сохранение результатов и журнала шагов | → Keycloak (JWKS); → Python / ML (обработка / поиск, результат возвращается в Java); → Генеративная LLM (генерация инсайтов); → PostgreSQL (чтение / запись); → Qdrant (индексация / поиск); → Файлы (PDF) |
| Python / ML | Компонент | Подготовка материалов: сбор новостей из RSS/API по команде Java, чтение PDF, очистка, разбиение на фрагменты; извлечение фактов, тем, факторов, отраслей и регионов; расчёт векторов фрагментов и поисковых запросов. Результат возвращает Java | ← Java; → Генеративная LLM (извлечение фактов); → Embedding-модель (векторы) |
| Генеративная LLM | Модель | По запросу Python — факты из текстов; по запросу Java — персональные инсайты, подробные разборы, ответы на вопросы на основе найденных источников и контекста компании | ← Python; ← Java |
| Embedding-модель | Модель | Векторы фрагментов и поисковых запросов для поиска по смыслу | ← Python |
| PostgreSQL | Хранилище | Компании, группы, платёжные связи, права доступа; метаданные документов и событий; инсайты, диалоги, журнал анализа, обратная связь | ← Java (чтение / запись) |
| Qdrant | Хранилище | Чанки PDF: векторы, тексты, номера страниц, documentId и метаданные для фильтрации. Возвращает тексты и ссылки на первоисточник вместе с результатами поиска | ← Java (индексация / поиск) |
| Файловое хранилище / volume | Хранилище | Оригиналы PDF; сведения о файлах и ссылки — в PostgreSQL | ← Java |

Стрелка в столбце «Взаимодействия» показывает инициатора обращения; ответ возвращается по той же связи.

**Распределение моделей** (настраивается конфигурацией, модели — только из разрешённого списка кейса):

| Задача | Вызывающий компонент | Модель |
|---|---|---|
| Классификация, извлечение фактов, тем и факторов из материалов | Python / ML | Gemma 4 26B A4B |
| Векторы фрагментов и запросов | Python / ML | Embedding-модель (см. AS-1) |
| Персональные инсайты, подробный разбор, критик | Java Backend | GLM-5.3-Flash |
| Уточняющие вопросы | Java Backend | Qwen3.6 35B A3B |
| Спорные случаи ранжирования, анализ связей | Java Backend | DeepSeek-V4.1-Flash (опционально) |

**Входные данные**

- CSV компаний, связей и платежей — импорт в Java, сохранение в PostgreSQL без вызова ML.
- PDF аналитики банка — загрузка через Java: оригинал в файловое хранилище, PDF в Python для извлечения текста и embeddings; готовые чанки Java записывает в Qdrant.
- Внешние новости — Java по расписанию вызывает Python; ручной текст или URL Java передаёт в Python напрямую.

**Основные потоки**

- *Вход:* Frontend → Keycloak (OIDC / PKCE) → токен → каждый запрос к Java с JWT; Java проверяет подпись по ключам JWKS и право пользователя на компанию (права хранятся в PostgreSQL).
- *Подготовка PDF:* Java → Python: чтение PDF, разбиение на чанки и расчёт embeddings → Python возвращает `chunks[]` с текстом, страницей, ordinal и вектором → Java записывает чанки в Qdrant и сохраняет только метаданные документа в PostgreSQL. Отдельных таблиц фрагментов и фактов нет. UUID документа связывает чанк с оригинальным PDF; UUID точки Java вычисляет из документа и ordinal.
- *Формирование кратких инсайтов:* Frontend → Java: профиль, группа, связи, кэш. Если актуальный результат есть — возвращается сразу. Иначе: Java формирует контекст и набор инструментов → LLM запрашивает поиск по теме → Java → Python (вектор запроса) → Qdrant (тексты чанков, страницы и оценки близости, с фильтрами) → PostgreSQL (метаданные документов) → LLM формирует инсайты → Java проверяет ссылки на фрагменты, сохраняет результат и шаги → Frontend. При недостатке оснований LLM запрашивает уточнённый поиск; число итераций ограничено, нехватка данных указывается в ответе.
- *Подробный разбор:* по нажатию, на основе сохранённого краткого инсайта и его оснований; при необходимости дополнительный поиск; результат сохраняется. Актуальность зависит от версии материалов, контекста компании и настроек анализа.
- *Уточняющий вопрос:* Frontend → Java → PostgreSQL (инсайт, профиль, история) → LLM → Java сохраняет вопрос и ответ → Frontend; при необходимости — цепочка Python → Qdrant → PostgreSQL → LLM.

**Контракт данных анализа и инсайтов.** Внутри цикла анализа используется JSON по схеме с полями `facts[]`, `bank_view[]`, `ai_inference[]`, `hypotheses[]`, `features_used[]`, `risks[]`, `opportunities[]`, `actions[]`, `missing_data[]`, `sources[]`, `trace_id`. У каждого элемента `bank_view` и `facts` — ссылка на фрагмент; у каждого `ai_inference` — поля `based_on` и `confidence`. Для загрузки PDF используется отдельный упрощённый контракт Python → Java с `chunks[]`: [инструкция ML-разработчику](../ml/ml-document-contract.md). Извлечение фактов и позиции банка выполняется при анализе найденных источников, а не как обязательный шаг индексации PDF.

**Безопасность AI-компонентов.** Идентификация через Keycloak, проверка JWT и прав на компанию в Java; инструменты только для чтения и выполняются Java; Java проверяет, что ссылки в ответе модели указывают на реально найденные фрагменты; фильтры поиска по области доступа в Qdrant; журнал всех шагов, вызовов и ошибок в PostgreSQL; allow-list источников; идентификаторы обезличены; внешние материалы — данные, не инструкции для агента.

## 3. Границы и ограничения

### 3.1 Объём первого релиза (MVP хакатона)

В объёме:

- FE-1 … FE-9 полностью; FE-10 … FE-12 в упрощённом виде (статичный граф влияния из JSON, кнопки обратной связи с записью в БД).
- Импорт трёх CSV кейса; загрузка девяти PDF; один RSS-источник; ручная загрузка текста/URL.
- Контекст компании с учётом группы и топ-N контрагентов по платежам.
- Вход через Keycloak с предзаданными тестовыми пользователями и правами на компании; набор демо-компаний (не менее трёх с разным профилем: кредитная нагрузка, ВЭД, плотный граф).
- Docker Compose, lock-файлы, README со сквозным сценарием проверки, THIRD_PARTY_NOTICES, синтетические тестовые данные, деплой на внешний сервер.
- Описание в README: метрики и процесс мониторинга качества, подход к масштабированию и сопровождению, место механизмов безопасности в архитектуре.


### 3.2 Последующие релизы (описываются, не реализуются)

- Новые источники: адаптер на источник, общий контракт результата обработки.
- Новые отрасли и типы клиентов: факторы влияния и правила ранжирования в конфигурации.
- Golden-set и регулярная оценка качества: precision релевантности на экспертной разметке, доля утверждений без
  источника, стоимость и задержка на инсайт, обратная связь пользователей и экспертов.
- Роли пользователей внутри компании с разными информационными потребностями.
- Уведомления, дайджесты, интеграция с реальными продуктовыми предложениями банка.

### 3.3 Вне объёма

- Закрытая интеграция с системами банка и реальным интернет-банком.
- Обучение собственных моделей; fine-tuning.
- Расчёт величины финансового эффекта (нет данных о затратах и договорах) — эффект описывается качественно с явным
  ограничением.
- Персональные инвестиционные рекомендации.
- Мобильное приложение; продуктивная аутентификация.

### 3.4 Ограничения

- Только LLM из разрешённого списка кейса; внешние AI-сервисы, автономные агенты и готовые мультиагентные системы не
  используются как основной компонент.
- Дневной лимит на LLM — 500 ₽.
- Срок — 5 дней разработки; коммиты после дедлайна не учитываются.
- Данные обезличены; идентификация реальных организаций и людей невозможна и не требуется.
- Решение должно устойчиво работать на неполных, неоднозначных и зашумлённых данных.

### 4.6 Критерии приёмки MVP

1. Один материал банка и связанная новость дают разные обоснованные выводы для нескольких компаний, включая влияние
   через группу или контрагента.
2. Новый материал и произвольная корректная компания обрабатываются общим алгоритмом без заранее написанного ответа.
3. У каждого разбора видны основания; отсутствие данных или позиции банка обозначено; уточняющий вопрос работает.
4. Повторный запрос использует актуальный результат; сбой ML или Qdrant даёт понятную ошибку и допускает повтор.
5. Запуск воспроизводим одной командой; тестовый вход описан; полный сценарий проходит по README.

## 6. Глоссарий

- **Инсайт** — вывод о значении события для конкретной компании, связывающий подтверждённые сведения с возможными
  последствиями и тем, что стоит проверить.
- **Краткий инсайт** — элемент ленты: заголовок, оценка влияния, однострочное объяснение.
- **Подробный разбор** — карточка по шести вопросам кейса с источниками.
- **Карта влияния** — граф «событие → факторы → признаки компании и контрагентов → риски/возможности → действия».
- **Фактор влияния** — канал, через который событие действует на бизнес: ключевая ставка, курс, цены на сырьё, спрос,
  регулирование.
- **Влияние второго порядка** — эффект события на компанию через её контрагентов или группу.
- **Embedding** — числовой вектор, представляющий смысл текста. **Vector store** — хранилище векторов с поиском по
  близости (Qdrant). **AI-оркестратор** — часть Java, управляющая шагами анализа и выполняющая инструменты.
- **Критик** — шаг цикла анализа, проверяющий полноту, непротиворечивость и привязку утверждений к источникам.
